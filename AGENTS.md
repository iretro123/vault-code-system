# Engineering rules

- Paid return memberships bind only via `claim_vault_return_membership`, which requires a fresh email-link (OTP) session plus a server-written proof row; sessions older than the bind never inherit it. Why: email auto-confirm means `email_confirmed_at` is not proof of inbox ownership.
- Past-due Stripe/return memberships lock all member content via `vault_payment_locked` (= `vault_billing_past_due` AND NOT `vault_access_for_user`, checked inside `can_use_free_community`); Stripe-linked allowlist rows are admission only, and unknown prices only reconcile an existing row bound to the same subscription/customer. Why: server RLS enforces billing, and the helpers must stay acyclic.
- Native GHL $1.99 memberships are provisioned only from the verified initial Stripe invoice (allowlisted price/product/location, settled $1.99 PaymentIntent) via `record_vault_ghl_invoice_payment`, gated by `VAULT_GHL_CHECKOUT_ENABLED=true`; rows with `source='ghl_native_invoice'` skip the generic price grant; missing GHL metadata/email/payment linkage is retryable (throw), wrong values are terminal. Why: GHL writes metadata seconds after invoice.paid; invoice flow has no Checkout Session, and a trialing price must never reach the generic grant.
- $49 mentoring entitlements are recorded only via `record_vault_mentoring_payment` after the re-read Stripe PaymentIntent, GHL order (allowlisted catalog product/price, our location) and GHL transaction (chargeId = PaymentIntent) all agree, gated by `VAULT_MENTORING_ENABLED=true`; Calendly single-use links are created at most once per entitlement (`begin_vault_mentoring_link`), and ambiguous link responses go to staff review, never auto-retry; mentoring is separate from membership access and refunds. Why: PaymentIntents carry no product, and Calendly link creation has no idempotency key.
